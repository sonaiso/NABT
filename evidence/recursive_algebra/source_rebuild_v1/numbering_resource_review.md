# حدود تنفيذ الرقم البنيوي في النواة المسلمة

النواة المسلمة تحدد `Tree.n` رقمًا بنيويًا بالنسبة إلى سجل قواعد ثابت؛ لا
يحمل هذا الرقم وحده موضع الوقوع أو سجل الشواهد أو نسخة قواعد متغيرة.
يحفظ `Tree.n` واسم الحامل الكامل وظيفتين مختلفتين يجب ألا تختلطا في
المحول أو في هدف شهادة إعادة الفحص.

## تعقيد تنفيذ `triangle`

في الملف المسلم، الأسطر 254–258، تعرف `triangle` بالرجوع على `Nat`:

```lean
def triangle : Nat → Nat
  | 0 => 0
  | n + 1 => triangle n + n + 1

def pair (a b : Nat) : Nat := triangle (a + b) + b
```

هذا تعريف صالح للبرهان، لكنه لا يقدم خوارزمية تنفيذ سريعة على أعداد
الأبناء الكبيرة. قبل استعماله في التصدير التنفيذي، يلزم بديل محسوب
للعدد المثلثي مع إثبات مطابقته، أو إبقاء هذا الرقم في الطبقة البرهانية
وحدها. لا تكفي سرعة العمليات الحسابية في تنفيذ Python لتثبت مطابقة
خوارزميتين مختلفتين في Lean.

## نمو طول العدد في الأشجار

حتى بعد استعمال الصيغة الحسابية المغلقة، يزيد الاقتران طول الرقم سريعًا.
في المثال الصغير `leaf (lexical 0)` يكون الرقم 6، وتكرر البانية الأحادية
ذات القاعدة صفر العلاقة:

`n_next = 3 * (n * (n + 1) / 2 + n) + 1`.

حُسبت أطوال البتات التالية محليًا بهذه العلاقة الحسابية، دون تنفيذ
`triangle` الرجوعية ودون إنشاء تمثيل عشري ضخم:

| عدد البنايات الأحادية فوق الورقة | طول الرقم بالبت |
|---:|---:|
| 0 | 3 |
| 1 | 7 |
| 2 | 14 |
| 4 | 56 |
| 8 | 892 |
| 12 | 14272 |
| 16 | 228347 |

هذه نتيجة حسابية محدودة لتقدير تكلفة التنفيذ، وليست إضافة مبرهنة إلى
النواة. البانية الثنائية تستعمل اقترانًا داخليًا إضافيًا، ولذلك يلزم
احتساب ميزانية الرقم نفسه، لا الاكتفاء بعدد عقد شجرة صغير أو حد عمق
موروث من محول آخر. يجب فحص ميزانية الحجم قبل إنشاء العدد الضخم أو
تحويله إلى JSON، وإرجاع حالة نفاد موارد مستقلة عن الرفض اللغوي.

تبقى مبرهنة الحقن غير المقيدة صحيحة داخل النموذج؛ حد التنفيذ ليس
ترخيصًا لغويًا ولا دليلًا على اكتمال البحث في المجال غير المحدود.
